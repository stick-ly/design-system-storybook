From one translation string to context-ranked answers

This is the coordination source of truth for changing Stickly’s translation, storage, review, dictionary, CEFR, and game systems from one canonical answer into a backward-compatible set of ranked translations for the meaning used in the current context.

The problem

Single-answer grading tests the database

Dictionary and CEFR words often have several valid translations. Without the learner’s original encounter, asking for one stored string rewards guessing Stickly’s preferred wording rather than recalling meaning.

The assumption is systemic

The singular string is currently display copy, persistence data, reverse-card source, game solution, inline-quiz key, edit target, export value, analytics payload, and part of highlight identity.

Context must choose the answer set

Multiple dictionary senses must not all become accepted answers. Stickly needs several natural translations for the specific sense expressed by the sentence around the word.

Hover resolution must be deliberate and bounded

A due-word quiz should resolve the sentence around the current highlight after intentional hover, reuse a bounded cache, and never penalize proficiency when resolution is unavailable or ambiguous.

Product critique and prototype decisions

Initial critique

“Most words have multiple possible translations. I need to find the one that’s requested of me … here I have nothing to hint at the one requested information.”

Decision: dictionary and CEFR review must identify a contextual sense and accept more than one natural answer.

Prototype request

Preserve the Piano-Tiles interaction while allowing the learner to commit to any accepted translation and narrow the remaining path as characters are selected.

Decision: use prefix-compatible candidates rather than one canonical solution.

Prototype correction 1

“We need to preview the next characters, not just the current row.”

Decision: the production design must use the existing stacked TileKit rows, not a one-row replacement.

Prototype correction 2

“The next row of characters is moving into place after selecting a correct character.”

Decision: rows remain keyed by stable position. The solved row uses the existing collapse animation and the next row physically moves into its place. Do not recreate the stack after each character.

Prototype correction 3

Use the characters from all accepted options at each position. Add or remove only trailing rows when the viable answer length changes.

Decision: characters from abandoned paths remain as stable distractors after narrowing; the board does not reshuffle.

Prototype correction 4

“When the user chooses the longer path, the distractors are missing from the rows.”

Decision: answer-derived characters are placed first, then every row is padded to the configured tile count with deterministic, language-aware distractors—including rows that only exist on the longer branch.

Scope expansion

This is a fundamental Stickly update: selection translation should offer ranked options and richer insight; the game consumes all accepted options; the inline quiz resolves the word in the sentence currently under the pointer using a quick cached request.

Inline-quiz continuation and repeat-hover critique

Show that another accepted answer continues beyond the current answer length without revealing its letters, preload an exact sentence occurrence on repeat hover, and remove the loading-state flicker.

Decision: render smaller, faint dashed continuation slots after the current candidate; remove them as the typed prefix eliminates longer branches. Cache the raw occurrence-scoped promise and its resolved value. A cache hit is applied before opening the bubble. During a first request, keep the quiz shell mounted and temporarily disabled under a quiet status instead of replacing the whole quiz with a loading card.

Fast dictionary-first architecture

Replace per-interaction OpenAI lexical enrichment with Microsoft Translator Dictionary Lookup. Start the contextual DeepL translation and dictionary lookup in parallel, persist lexical results on the word, and reuse those options in every later hover quiz and tile-game challenge.

Decision: DeepL remains the primary contextual translation. Microsoft dictionary translations are additional accepted answers and carry confidence, part of speech, prefixes, and compact back-translations. OpenAI runs only once when Microsoft returns no usable dictionary entry or does not support the language pair. Missing dictionary data is omitted rather than surfaced as an error.

TileKit row-count correction

Every row in one challenge must contain the same number of tiles. The bug was not tile width: individual rows were independently increasing their tile count when several answer branches contributed different characters.

Decision: the existing challenge distractor budget determines one tile count, and every row is padded to exactly that count. Retain the original translation first, then retain only ranked alternatives whose character branches fit that budget. Do not alter tile dimensions or expand individual rows for synonyms.

TileKit column-randomization correction

Stable rows accidentally left answer-derived characters in the leading columns. This made distractors cosmetic: the player could repeatedly choose the left tile instead of reading the alternatives.

Decision: shuffle every completed row with a challenge-seeded order. Tile order remains stable while the player follows a branch, but changes for a new challenge. The existing difficulty-controlled tile count continues to determine how many choices the player must distinguish.

Microsoft back-translation critique

Forward dictionary alternatives are not enough for bidirectional practice. For example, English meet can produce German begegnen and entsprechen; a reversed entsprechen challenge also needs that exact entry’s back-translations such as match and correspond.

Decision: persist Microsoft back-translations on each translation option, retain the full dictionary entry as a compatibility fallback, and build reverse challenges per sense. Never merge back-translations from sibling target-language meanings.

CEFR dictionary parity critique

Supporting Microsoft options for stored personal vocabulary is insufficient if the CEFR test still ships OpenAI-only answer sets and tests only the learning-to-native direction.

Decision: enrich generated CEFR decks with Microsoft Dictionary during administrative prewarming, retain OpenAI options as the non-blocking fallback, and mix forward and reverse challenges in the assessment UI. Reverse prompts use only the selected dictionary sense’s back-translations.

Target additive contract

translation remains the primary display value for old clients. New clients normalize legacy records to one accepted option. “Related” meanings are visible insight but never silently accepted in review. 

interface TranslationOption {
  id: string;
  text: string;
  rank: number;
  senseId?: string;
  partOfSpeech?: string;
  status: 'accepted' | 'related';
  source: 'user' | 'deepl' | 'openai' | 'dictionary';
}

interface ContextualAnswerSet {
  options: TranslationOption[];
  primaryOptionId: string;
  contextFingerprint?: string;
  schemaVersion: 2;
  resolvedAt?: number;
}

Persisted words use translationOptions?: TranslationOption[] and translationOptionsVersion?: number. ContextualAnswerSet is the transient resolver response, not a nested persisted word field.

Compatibility invariants

  • Never change translation from string to array.
  • Never infer reverse-direction options.
  • Old clients may ignore options; new clients must tolerate their absence.
  • Manual translations stay the learner’s primary memory hook.

Privacy and cost invariants

  • Do not log page sentences or raw context.
  • Resolve current context only after intentional hover.
  • Cache by normalized context fingerprint, language pair, schema, and model.
  • Static CEFR and dictionary options are generated once, not per play session.

Production TileKit acceptance criteria

  1. FlashCard.acceptedAnswers always contains canonical flipside.
  2. The service maintains the typed prefix and viable candidate set.
  3. A character succeeds when any accepted answer begins with the attempted normalized prefix.
  4. Each row initially contains the union of accepted-answer characters at that position.
  5. Remaining tile slots receive deterministic language-aware distractors.
  6. Row identity and tile order remain stable after a branch; abandoned options become distractors.
  7. The solved row collapses through the existing TileRow animation and the next row moves into place.
  8. Only trailing rows are added or removed when maximum viable answer length changes.
  9. Longer-only rows retain a full distractor set.
  10. The power-up removes characters invalid for the current prefix, not merely characters unlike flipside.
  11. Completion speaks and records the answer actually built while SRS remains attached to the stored word.
  12. The production Storybook story uses the real game service and TileKit; the prototype is removed after parity.
